# 项目说明

## 一、项目定位

**一句话定义**：做一个面向经营分析场景的智能分析 Agent，在指标语义约束下完成自然语言问题理解、查询生成、结果校验与分析输出，并验证其比普通问数流程更可靠。

---

## 二、最小系统范围（MVP 定义）

为保证本科毕设可落地，MVP 版本严格控制在以下范围内：

### 2.1 支持的场景
- 场景：**零售/电商经营分析**（基于公开数据集）
- 交互方式：**单轮自然语言提问 + 可选简单追问**
- 输出形式：**SQL 语句 + 执行结果表格 + 简要文字洞察**

### 2.2 数据规模
- 表数量：4 张核心表（订单事实表、客户维表、商品维表、时间维表）
- 数据量：10,000 ~ 100,000 条订单记录
- 时间跨度：12 ~ 24 个月

### 2.3 支持的指标数量
- 核心指标：**5 个**（MVP 先做 5 个，再扩展到 8 个）
  1. 销售额
  2. 订单量
  3. 客单价
  4. 新客数
  5. 复购率
- 扩展指标（可选）：活跃客户数、商品转化率、区域销售占比

### 2.4 支持的问题类型
| 类型 | 说明 | 示例 |
|------|------|------|
| 直接统计 | 某指标在某时间/维度下的数值 | "上月销售额多少？" |
| 趋势分析 | 某指标的时间序列变化 | "近 6 个月销售额趋势" |
| 对比分析 | 不同维度或时段的对比 | "华东 vs 华北的销售额对比" |
| 排名分析 | Top N / Bottom N 分析 | "销售额最高的前 10 个商品" |
| 占比分析 | 某维度下的指标构成 | "各品类销售额占比" |
| 异常识别 | 波动较大的时段/维度 | "销售额环比下降最大的月份" |

### 2.5 不纳入 MVP 的功能
- 复杂归因分析（"为什么下降"的多步骤自动归因）
- 多步骤自主分析（Agent 自动拆解多步分析计划）
- 多表复杂关联查询（超过 3 张表的 join）
- 自定义指标即时定义
- 权限控制和多租户

## 三、系统模块设计

### 3.1 模块划分

MVP 系统划分为 6 个核心模块：

| 模块 | 职责 | 输入 | 输出 |
|------|------|------|------|
| 1. 任务理解模块 | 解析自然语言问题，提取指标、维度、时间、问题类型 | 用户问题 NL | 结构化任务描述（JSON） |
| 2. 指标语义匹配模块 | 将问题中的业务术语匹配到标准指标定义，补全口径约束 | 任务描述 + 语义规则库 | 对齐后的指标规范对象 |
| 3. 执行规划模块 | 生成查询执行计划（涉及的表、join 方式、分组维度） | 指标规范对象 + 表结构 | 执行计划（query plan） |
| 4. SQL 生成模块 | 在语义约束下生成可执行 SQL | 执行计划 + 表结构 | SQL 语句 |
| 5. 结果校验模块 | 检查 SQL 执行结果是否符合指标口径、时间约束、维度限制 | SQL + 执行结果 + 指标规范 | 校验报告（通过/不通过+修正建议） |
| 6. 洞察生成模块 | 对结果进行总结，生成经营分析风格的文字说明 | 执行结果 + 指标定义 + 问题类型 | 文字洞察 + 简单图表建议 |

### 3.2 基线系统（Baseline）

**基线方案**：不带语义约束的常规 Text-to-SQL 流程

即：直接将自然语言问题 + 数据库 Schema 输入 LLM，让其直接生成 SQL，不经过指标语义匹配、口径校验和结果检查环节。

```
基线流程：
NL Question + DDL Schema → LLM → SQL → 执行 → 结果
```

**实验组（Ours）**：加入指标语义约束的 Agent 流程

```
实验组流程：
NL Question → 任务理解 → 指标语义匹配 → 执行规划 → SQL生成 → 结果校验(可自修正) → 洞察生成
              ↑                                                        |
              |_________________ 语义规则库 ___________________________|
```

### 3.3 对比维度

实验组 vs 基线组，在以下维度对比：

| 维度 | 说明 |
|------|------|
| SQL 执行成功率 | 生成 SQL 能否无错误执行 |
| 指标语义一致性 | 计算口径是否与标准指标定义一致 |
| 任务完成率 | 是否完整回答用户问题 |
| 平均修正次数 | 需要人工/自修正的次数 |
| 人工修正成本 | 人工修正需要的时间/步骤数 |

## 四、最终想展示的核心结果

### 4.1 系统 Demo 展示
- 输入 5~10 条典型经营分析问题，现场演示 Agent 完整流程
- 对比展示：同一条问题，基线 SQL vs 语义约束 SQL 的输出差异

### 4.2 实验定量结果
- 20~30 条测试问题上的 5 项评测指标对比表格
- 至少 1~2 张对比柱状图（实验组 vs 基线组）
- 错误案例分析（基线组常见错误类型 + 语义约束如何修复）

### 4.3 论文核心结论
1. 指标语义约束机制在经营分析场景下能有效提升 SQL 的业务正确性（不仅仅是语法正确性）
2. 结果校验与自修正模块能降低人工修正成本
3. 构建的指标语义规则库和测试问题集可复用为该方向的小型基准
