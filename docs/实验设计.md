# 实验设计

## 一、实验目标

通过与"不带语义约束的基线问数流程"进行对比，验证引入**指标语义约束机制**后，智能分析 Agent 在以下维度的改善：

1. SQL 执行成功率（语法层面 + 数据层面）
2. 指标语义一致性（业务口径层面）
3. 任务完成率（用户需求层面）
4. 平均修正次数（系统稳定性层面）
5. 人工修正成本（用户实际使用成本层面）

---

## 二、实验分组

### 2.1 基线系统（Baseline）

**系统定义**：常规 Text-to-SQL 流程，不做指标语义匹配和结果校验。

```
输入：
  (1) 用户自然语言问题
  (2) 数据库 DDL（4 张表的建表语句）
  (3) 样例数据（可选）

执行：直接输入 LLM，要求生成 SQL → 执行 SQL → 返回结果
```

**典型风险**：
- GMV / 成交额等别名被 LLM 误解为"所有下单金额（含未支付+退款）"
- 客单价分母误用 COUNT(*) 行数而不是 DISTINCT 订单
- 复购率误用订单维度而非客户维度
- 时间范围理解偏差（例如"上月"被误算成近 30 天）

### 2.2 实验组（Ours）

**系统定义**：加入指标语义约束机制的智能分析 Agent，包含完整 6 模块。

```
NL 问题
  → 任务理解（提取指标/维度/时间/类型）
  → 指标语义匹配（按 metric_semantics.json 对齐标准口径 + 补全局过滤）
  → 执行规划（表、join、分组）
  → SQL 生成（受语义模板约束）
  → 结果校验（检查：pay_status过滤、DISTINCT订单、时间范围正确性；不通过则自修正）
  → 洞察生成
```

## 四、评测指标

### 4.1 SQL 执行成功率（Execution Rate）

**定义**：生成 SQL 在数据集上**无报错运行**的比例。

```
SQL 执行成功率 = 成功执行的问题数 / 总问题数 × 100%
```

**判定规则**：
- ✅ 通过：SQL 无语法错误、无列/表不存在错误、无除零错误，返回结果表
- ❌ 失败：任何运行时错误 / 超时（>10s）

### 4.2 指标语义一致性（Semantic Accuracy）

**定义**：SQL 执行结果**在数值上与参考 SQL（标准口径）一致**的比例。允许 ±0.01% 的浮点差异。

```
指标语义一致性 = 结果完全一致（或误差 ≤ 0.01%）的问题数 / 成功执行的问题数 × 100%
```

**常见不一致类型**：
1. 金额类：忘记加 pay_status='已支付' → 金额虚高 15%~20%
2. 订单类：DISTINCT order_id 漏掉 → 订单量偏大（按行数算）
3. 复购率：分母用订单数不用客户数 → 数据完全错位
4. 新客数：按注册日期不是首单日期 → 偏差 10%+
5. 客单价：分母是客户数不是订单数 → 含义变了
6. 时间范围：把"上月"算成"近 30 天" → 数据错位

### 4.3 任务完成率（Task Completion Rate）

**定义**：输出结果**在语义上完整回答了用户问题**的比例。由人工标注（0/1 二分类）。

```
任务完成率 = 标注为"完整回答"的问题数 / 总问题数 × 100%
```

**判定示例**：
- 问"各品类销售额 Top 3"，只返回了品类销售额但没排序取 Top 3 → 语义一致=通过，任务完成=不通过
- 问"同比增长"，返回了今年和去年但没算增长率 → 部分完成=不通过

### 4.4 平均修正次数（Avg. Corrections）

**定义**：对每条问题，系统从"初次输出"到"获得通过结果"所需的**自修正轮次 + 人工修正轮次**的平均值。

```
平均修正次数 = Σ（每条问题的总修正次数） / 总问题数
```

说明：
- 基线系统不支持自修正，因此修正次数 = 人工修正次数（通常 0~3 次）
- 实验组支持 1~2 次自修正，目标是人工修正次数显著降低

### 4.5 人工修正成本（Human Correction Cost）

**定义**：人工修正一条问题结果所需的**预估操作时间（秒）**。采用标准估算：

| 操作 | 预估耗时 |
|------|---------|
| 无需修改 | 0 秒 |
| 修改 SQL 中一个过滤条件（如加 pay_status） | 20 秒 |
| 修改 SQL 中一个公式（如客单价分母改为 DISTINCT） | 40 秒 |
| 重写整条 SQL | 90 秒 |
| 重写 + 重新理解口径 | 150 秒 |

```
人工修正总成本 = Σ 每条问题的修正操作耗时
平均人工修正成本 = 总成本 / 总问题数
```

## 五、数据记录方式

### 5.1 实验记录表格式（CSV / Excel）

| 列名 | 说明 |
|------|------|
| question_id | 问题编号（Q01~Q25） |
| group | 实验组 / 基线组 |
| generated_sql | 生成的 SQL 语句 |
| exec_success | 执行是否成功（1/0） |
| exec_error_msg | 若失败，错误信息 |
| result_match_reference | 结果与参考 SQL 是否一致（1/0 / "部分一致"） |
| mismatch_type | 若不一致，错误类型（1.未过滤pay_status / 2.漏DISTINCT / 3.复购率口径错 / 4.新客口径错 / 5.时间错 / 6.其他） |
| task_complete | 任务是否完成（人工标注 1/0） |
| self_correction_rounds | 系统自修正次数 |
| human_correction_rounds | 人工修正次数 |
| human_correction_seconds | 人工修正预估耗时（秒） |
| remarks | 备注 |

### 5.2 记录时机
- 每条问题都记录基线组和实验组**单独跑**的结果
- 记录人：本人（陈琦）
- 必要时，可以截图保存 SQL 和结果，归档到 `outputs/reports/`

### 6.3 案例深度展示
挑选 3 条典型问题做 Case Study：

| 案例 | 选择意义 |
|------|---------|
| 案例 1：销售额 + pay_status 过滤 | 展示最简单直接的口径提升 |

| 案例 3：新客数（首单时间 vs 注册时间） | 展示业务定义的重要性 |

每个 Case 呈现：
- 自然语言问题
- 基线生成的 SQL（及错误点）
- 实验组生成的 SQL（及正确点）
- 两者结果对比数字

## 七、实验前置检查清单

开始正式记录实验前，确认：
- [ ] 实验数据集已导入 SQLite / PostgreSQL，表名与字段名完全一致
- [ ] 参考 SQL 每条都在真实数据上跑过，结果可信
- [ ] LLM API Key 配置就绪，温度参数固定（baseline 与实验组使用相同温度 = 0）
- [ ] 基线系统的 Prompt 模板已确定（避免因 Prompt 不一致导致评测不公）
- [ ] 实验记录表模板已建好（outputs/reports/experiment_records.csv）
- [ ] 实验者已熟悉每条问题的标准答案和错误类型
